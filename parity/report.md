# Settlement parity

Generated by `make parity` (tools/parity/settlement_parity.py); the same
verdicts are in parity/report.json.
Each row replays a `transcripts/settlement_*.json` scenario against the
settlement service on 8083 and compares the four things ADR-001:82-90
calls parity: status class, business fields, validation keys, db state.

Scenarios listed in `parity/routes.json` are approved differences: they
are judged against their `docs/changes/CHG-nnn` record and reported as
CHANGED, and still fail on anything the record does not approve.

| Scenario | Legacy behaviour | Verdict | Difference |
| --- | --- | --- | --- |
| `settlement_bad_deductible` | Settlement with a non-numeric deductible | CHANGED (CHG-001) | A non-blank, unparseable deductible is a validation error instead of the error screen |
| `settlement_blank_deductible` | FNOL settlement with a blank deductible | PASS | - |
| `settlement_calculate` | Calculate a standard settlement | PASS | - |
| `settlement_deductible_floor` | Settlement floored when deductible exceeds the loss | PASS | - |
| `settlement_half_cent` | Settlement using double half-cent rounding | PASS | - |
| `settlement_policy_cap` | Settlement capped by the policy limit | PASS | - |
| `settlement_save` | Save the calculated settlement | PASS | - |

Status class: the legacy error path forwards to `error.jsp` with a 200;
ADR-001:51,84 replaces that forward with the equivalent error status
class, so a 5xx there is parity, not a change.

# Payment parity

Generated by `make payment-parity` (tools/parity/payment_parity.py); the
same verdicts are in parity/report.json, and parity/report.html shows each
scenario's request, expected against actual, and the rules it covers.
Each row replays a payment transcript or a numbered live request of
`docs/specs/SPEC-PAY-001-live.json` against the payment service on 8084
and compares what ADR-002 ("How parity is judged") calls parity: status
class and redirect target, business fields, validation keys, history
links, payee and method as displayed, and database state.

The live requests run in their recorded order from the seed. L02 and L35
(sign in) and L05 (settlement save, applied as
`parity/preconditions/payment/settlement-save.sql`) are setup, not
scenarios. `payment_live_db_after` compares the database afterwards with
the `db_after` queries of the live file.
