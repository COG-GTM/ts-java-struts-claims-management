# Known legacy quirks

Behaviours of the Struts monolith that look like bugs, are relied on by the
recorded transcripts, and are therefore reproduced deliberately by the
extracted settlement service. Each one is preserved on purpose: SPEC-SETTLE-001
treats the legacy screens as the specification, so "fixing" any row below
changes observable behaviour and breaks parity (`make parity`).

Anything a later rewrite is likely to tidy away should be listed here with the
test or transcript that will catch the tidy-up.

| Id | Behaviour | Where in the legacy code | How found | Where the service reproduces it | Rules |
| --- | --- | --- | --- | --- | --- |
| QUIRK-01 | The settlement amount is rounded with binary double arithmetic, `Math.round(amount * 100.0) / 100.0`. Half cents do not round half-up: `1.005 * 100.0` is `100.49999999999999`, so 1.005 settles at 1.00. Replacing the doubles with `BigDecimal("1.005").setScale(2, HALF_UP)` would give 1.01 and change the money paid out. | `src/main/java/com/northstar/claims/service/SettlementCalculator.java:37` | Read while writing SPEC-SETTLE-001; pinned by capturing `transcripts/settlement_half_cent.json` against the running monolith | `services/.../domain/SettlementCalculator.java:52` (same statement). Guarded by `SettlementCalculatorTest.halfCentRoundsDownAndOnlyTheSettlementAmountIsRounded` and `SettlementCalculateEndpointTest.halfCentUsesLegacyDoubleMath`, which fail if the calculator is moved to decimal arithmetic | SETTLE-R15 (v2), SETTLE-R16 |
| QUIRK-02 | Display formatting is a *second*, independent rounding: `<ns:field type="money">` runs `String.format("%.2f", ...)` over every money field, including `coveredAmount`, which the calculator leaves unrounded (SETTLE-R17). The two roundings disagree, so one screen shows covered 1.01 next to settlement 1.00 for the same 1.005 input | `src/main/java/com/northstar/claims/web/tag/FieldTag.java:52-59` | Read while writing SPEC-SETTLE-001; the disagreeing pair is visible in `transcripts/settlement_half_cent.json` | `services/.../web/FieldFormatter.java:38-40`, applied in `SettlementController.calculateFields`. Guarded by `SettlementCalculateEndpointTest.halfCentUsesLegacyDoubleMath` (asserts 1.01 and 1.00 together) | SETTLE-R20 (v2), SETTLE-R21 (v2) |
| QUIRK-03 | On the calculate path a claim that does not exist, or a claim whose policy does not exist, does not fail: the policy limit silently falls back to 10000 and the request returns a settlement | `src/main/java/com/northstar/claims/web/SettlementCalculateAction.java:25-31` | Read in the action, then confirmed by hand against the running monolith with `claimId=9999` (returns 90.00 uncapped, and 10000.00 capped at covered 20000) — the evidence recorded in SETTLE-R08 (v2) | `services/.../web/SettlementController.java:68,97` (`FALLBACK_POLICY_LIMIT`, `.orElse(...)`) | SETTLE-R08 (v2) |
| QUIRK-04 | The save path does *not* share that fallback: it dereferences the claim and its policy without a null check, so the same missing claim that calculates happily raises an exception and lands on the error screen. Calculate and save therefore disagree about the same claim id | `src/main/java/com/northstar/claims/web/SettlementSaveAction.java:25-33` | Read while comparing the two actions for SPEC-SETTLE-001; the asymmetry is not visible in any single transcript | `services/.../web/SettlementController.java:114` (`.orElseThrow(MissingClaimException::new)`, deliberately not `.orElse(FALLBACK_POLICY_LIMIT)`) | SETTLE-R26, SETTLE-R08 (v2) |
| QUIRK-05 | The error screen answers HTTP 200. The global Struts exception mapping *forwards* to `error.jsp`, so a failed settlement is a 200 response with no business fields, and — because the settlement actions run with `validate="false"` — no validation error keys either. Nothing in the response body marks it as a failure except the screen name | `src/main/webapp/WEB-INF/struts-config.xml:59-60` (global exception forward), `:206-222` (`validate="false"`) | Found by capturing `transcripts/settlement_bad_deductible.json`: status 200, empty `business_fields`, empty `validation_errors` | Not reproduced: `services/.../web/SettlementErrorHandler.java` answers 500 with the same empty fields and empty errors. This is the one approved difference, recorded as CHG-001 (`docs/changes/CHG-001-error-status-class.md`) and declared in `parity/routes.json`, so `settlement_bad_deductible` replays as CHANGED rather than PASS | SETTLE-R06, SETTLE-R09 |
| QUIRK-06 | Request parameters fall back silently. A missing or unparseable `claimId` becomes 119, `coveredAmount` becomes 5000, `depreciation` becomes 0, and a blank `deductible` becomes `"0"` — all inside `catch (Exception)` blocks, so a typo in a request yields a plausible settlement for the wrong claim instead of an error | `src/main/java/com/northstar/claims/web/ClaimsActionSupport.java:31-45`; `src/main/java/com/northstar/claims/web/SettlementCalculateAction.java:23,32-37` | Read in the action support class; the blank-deductible half is observed in `transcripts/settlement_blank_deductible.json` | `services/.../web/LegacyParameters.java:21-23,29-52` (`DEFAULT_CLAIM_ID`, `DEFAULT_COVERED_AMOUNT`, `DEFAULT_DEPRECIATION`, `deductibleOrZero`) | SETTLE-R02, SETTLE-R03, SETTLE-R04, SETTLE-R05 |
| QUIRK-07 | Every saved settlement is stamped with the literal date `2019-04-01`. It is a hard-coded string, not the current date, so `calculated_date` says nothing about when a row was written | `src/main/java/com/northstar/claims/web/SettlementSaveAction.java:34-38` | Read in the save action while writing SETTLE-R27 | `services/.../web/SettlementController.java:124` (the literal `"2019-04-01"` passed to `StoredSettlement`) | SETTLE-R27 |

`services/...` above is short for
`services/settlement-service/src/main/java/com/northstar/settlement/`, and test
classes live under `services/settlement-service/src/test/java/com/northstar/settlement/`.
