### SETTLE-R06 (v2)

Introduced at spec 0.4 in [`5f4260c`](https://github.com/COG-GTM/ts-java-struts-claims-management/commit/5f4260cafe44d1c6468a10347433448f6f081112) (2026-09-23): CHG-001: invalid deductible becomes a validation error in the settlement service.

Rule history: Version 0.4: an unparseable non-blank deductible becomes a validation error (status 200, calculate screen, no business fields, key `settlement.deductible.invalid`) on calculate and on save, with no row written, per docs/changes/CHG-001-invalid-deductible.md; v1 text retained above as the legacy behaviour

**Before — SETTLE-R06 (v1)**

> A non-empty, non-numeric `deductible` is passed to `Double.parseDouble` unguarded; the resulting exception is handled by the global exception mapping and the request is forwarded to `/WEB-INF/jsp/error.jsp` with status 200 and no validation errors.
>
> Observed: [`settlement_bad_deductible`](../../transcripts/settlement_bad_deductible.json)<br>Read: [`src/main/java/com/northstar/claims/service/SettlementCalculator.java:28`](../../src/main/java/com/northstar/claims/service/SettlementCalculator.java#L28); [`src/main/webapp/WEB-INF/struts-config.xml:59-60`](../../src/main/webapp/WEB-INF/struts-config.xml#L59-L60)

**After — SETTLE-R06 (v2)**

> A `deductible` that is not blank and does not parse as a number is rejected before the calculation and before any write: the response is status 200 on the calculate screen, with no business fields and exactly one validation error, key `settlement.deductible.invalid`. The same check runs on the save path ahead of the insert, so no SETTLEMENT row is written. A blank (null, empty or whitespace-only) `deductible` still counts as 0 per SETTLE-R05. This is a deliberate difference from the legacy behaviour of v1, which the monolith keeps; it applies to `services/settlement-service` only.
>
