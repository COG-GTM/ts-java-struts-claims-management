## How this spec changes

Rule ids are permanent and rule text is append-only: a rule is never rewritten in
place, a new version of the same id is added beside the old one, the old heading
is marked superseded, a Rule history row is added, and the spec `Version:` is
bumped. The history above shows three distinct reasons for a change, and each
leaves a different trail.

1. **A correction of a misread** — the legacy code or a transcript was read
   incompletely or wrongly, so the rule text is revised, but nothing about the
   system's behaviour changes. Trail: a new rule version, a Rule history row, no
   `docs/changes/CHG-nnn` record, no entry in `parity/routes.json`.
   Example: SETTLE-R08 (v1) was superseded by SETTLE-R08 (v2) in `2a5ef42` (2026-09-23, "SPEC-SETTLE-001 v0.2: evidence for the 10000 limit fallback; add OPEN-QUESTIONS"); the Rule history row for SETTLE-R08 (v2) reads: Version 0.2: added live-run evidence for the 10000 fallback (claimId 9999 returns 90.00 uncapped, and 10000.00 capped at covered 20000); v1 text retained above. No change record is cited, the monolith and the service behave as before, and the parity verdicts are untouched.

2. **An approved behaviour change** — the extracted service is required to behave
   differently from the monolith. Trail: a new rule version whose text names the
   `docs/changes/CHG-nnn` record (`Approved:`), the record itself, tests that cite
   the new version, and an `approved_differences` entry in `parity/routes.json`;
   the legacy version is kept as the monolith's behaviour.
   Example: SETTLE-R06 (v1) was superseded by SETTLE-R06 (v2) in `5f4260c` (2026-09-23, "CHG-001: invalid deductible becomes a validation error in the settlement service"), which cites `docs/changes/CHG-001`. The same commit added the record, the tests that cite SETTLE-R06 (v2), and the `approved_differences` entry in `parity/routes.json`, so `make parity` reports the affected transcript as CHANGED rather than PASS or FAIL.

3. **An open question** — the reading is correct but it is not known whether the
   behaviour is intended. Trail: a row in `docs/specs/OPEN-QUESTIONS.md` naming the
   rule, with an interim decision; the rule itself is unchanged until the owner
   answers, at which point the answer arrives as one of the two kinds above.
   Example: OQ-01, added in `2a5ef42` (2026-09-23, "SPEC-SETTLE-001 v0.2: evidence for the 10000 limit fallback; add OPEN-QUESTIONS"), asks: "Is the 10000 policy-limit fallback used when a claim or its policy cannot be found (SPEC-SETTLE-001 SETTLE-R08 v2) a business rule, or a leftover default in the code?" It blocks SPEC-SETTLE-001 SETTLE-R08; its status is Open. The rule it names keeps its current text (SETTLE-R08 (v2)), and no new version of SETTLE-R08 has been added since.
